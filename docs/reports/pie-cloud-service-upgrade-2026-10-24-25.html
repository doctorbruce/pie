01 WHAT “STATELESS” MEANS HERE

不是没有状态，而是不依赖固定实例

模型上下文、Promise 和取消信号在执行时存在于内存很正常。问题在于：实例退出后，下一台机器能否从外部事实判断发生过什么，并在安全位置继续。

执行时有状态

Agent、工具调用、工作上下文都是本次执行的临时对象。它们不需要被序列化搬走。

服务可替换

关键事实在共享存储中。实例换掉后，可按权限与归属重新装载，不依赖原进程常驻。

任务可恢复

从已提交输入、工具结果或可查询外部任务继续；不是恢复未保存 token 或异步函数现场。

这轮真正改变的依赖关系

从“这个对象一直活着，所以能继续”，转为“持久事实足够，所以对象可以重建”。这为滚动更新、实例替换与多实例接管提供基础，但生产归属和调度仍由 Cloud 完成。

术语：Assistant 是角色配置；Session 是持久会话；Turn 是一次完整用户提交；Agent 是执行对象。Runtime 是管理这些语义的共享层，不是某个助手的 prompt 模板，也不是一用户必须常驻一个 Agent。

恢复模型：Turn → ToolExecution。Job 只是外部执行器适配名称，不是顶层恢复对象。普通调用 inline、委派 delegated、持久外部执行 durable 共用执行身份与事实记录；不意味着所有模式都支持跨进程续跑。

02 THE CHANGES

六条主线，把“可重建”落到实际路径

10 月 24—25 日补装载、读取边界与任务接管；26 日新增统一执行账本，并纳入同工作树的流式工具提前执行。后者是时序优化，不是新增流中断恢复。保留原文件名，日期与验收更新至 26 日。

01

只装载被访问的会话，空闲后可释放整个 Session

以前：loadSessions() 把范围内全部 Session 元信息放进 Runtime。只访问 A，也要承担许多冷会话的对象成本。

现在：启动不查询会话；按 ID 读取，列表独立分页。同 ID 并发访问合并装载，未恢复的 running 会话只影响目标访问。启用卸载策略后，可靠收尾且无引用时回收整个 Session。

对 agent-service：冷启动和闲置执行态不再必然随用户全部历史会话一起增长。不是测得的 RSS 承诺；Cloud 工厂和 Store 也要迁移。
接口与安全保护
  • readSession(id) + listSessions({ limit, cursor })；列表不激活 Agent、不读正文。
  • 排序使用 updatedAt 与 ID 双键；父会话删除查询未装载子会话。
  • 执行、确认、后台任务、读操作及写入失败阻止不安全释放；订阅可保留轻量元信息。
02

不是读完再切片，而是在存储查询里停止

以前：分页或恢复检查可能先走完整条祖先链。API 看似只拿一页，底层仍承担长历史成本。

现在：readHistory 累计页大小加一的候选节点后停止；工作窗口到压缩边界停止；readTurnPath 只读当前 Turn 的输入到叶子。

对 agent-service：给远端 Store 明确的读取边界，减少旧历史对普通读取、恢复判定和模型准备的牵连。SQLite 优化不会自动优化 MySQL。
仍然可能昂贵的路径
  • 完整树、导出、显式全量快照、未知结果失败修复可能全量读取。
  • 单条大消息、超长当前 Turn 以及无压缩边界的工作上下文仍不保证固定成本。
  • 页大小约束节点数量，不等于消息字节数、总缓存或事件缓冲已有上限。
03

保持原 Turn，在已提交消息边界恢复

以前：读到历史不等于知道从哪继续；重新提交用户输入，可能重复执行有副作用的工具。

现在：持久化输入节点、实际 prompt 与取消意图；共享判定 + resumeTurn 保持原用户输入、Turn/request ID 和已应用配置。准入保存成功后才调用模型。

对 agent-service：实例替换有统一恢复语义，不必靠新建 Turn 或复制消息猜测续跑位置。Cloud 仍须先取得归属、核对工具事实并隔离旧 owner。
恢复边界
  • 输入或整批工具结果已提交：继续；最终 Assistant 已提交：仅补结算。
  • 工具结果未知且没有有效外部关联：拒绝盲目重放。
  • 无效/跨分支/循环路径安全拒绝，存储错误不伪装成恢复成功。
04

异步任务靠持久 ID 接回结果，不靠原回调

以前：任务可能还在远端跑，但实例的 Promise 和 callback 消失了。新实例不知道该找谁。

现在：工具调用可选 context.runJob，先原子保存稳定关联与提交意图，收到执行器确认后记录 submitted。新实例只查询原任务；明确结果、终态账本和恢复准入同事务提交后继续原 Turn，不重新 submit。

对 agent-service：可映射已有账本与 Worker 状态；通知仅负责唤醒，持久查询才是事实来源。关闭解除等待，显式取消才请求远端取消。
能力不是自动套在所有 job 上
  • 宿主必须实现并注入 DurableJobExecutor，持久映射稳定 ID 与远端 taskId。
  • 原 Shell、后台 Subagent、内存 BackgroundJobs 不自动持久化。
  • Worker 自身中断后从哪继续，仍由工具内部 checkpoint/幂等策略决定。
05

统一执行账本，记录工具到达过的确定边界

以前：checkpoint 会在终态清理，Promise 或执行函数返回也不能证明结果已可靠保存。重建对象和查到历史，仍不足以说明工具到了哪一步。

现在：工具开始前保存 started，外部提交前保存 submission_intent，实际收到确认后保存 submitted。后处理后的结果与 completed / failed 同事务落盘；未知边界可记 recovery_required，不伪造成功或撤销事实。

对 agent-service：不同实例可核对同一 Session/Turn/toolCall 的稳定执行事实。账本与历史矛盾时先拒绝，不查询执行器、不创建 Agent；写入屏障失败后不能绕过账本单独保存结果。
模式、分页与保留规则
  • 普通工具默认 inline，内置 Task 为 delegated，runJob 关联外部执行后为 durable。只声明模式不会赋予接管能力，也不同于串行/并行的 executionMode。
  • 账本独立追加，不塞进 Session 或 checkpoint；结果正文仍在历史中。稳定记录 ID 去重，身份冲突拒绝。
  • readToolExecutions(sessionId, { turnId, limit, afterSeq? }) 每页 1–200 条。账本 seq、历史 seq、事件 revision 各自独立。
  • 终态、下一轮和重启保留账本，删除 Session 才级联清理。普通列表、快照和 SSE 不携带完整账本。
  • recovery_required 不是公开 Turn 新状态；硬退出可能来不及写它。没有 submitted 不能证明远端没执行，恢复仍只查原 ID。
06

完整工具调用可提前启动，但恢复仍保守

以前：通常等整条模型响应结束后才执行工具，即使一个调用已经完整，仍需等待剩余输出。

现在：收到明确的 toolcall_end 且原始参数可严格解析时，可以提前执行；工具开始前保存 pendingAssistant 调用快照与 started。下一次模型请求仍等待本条响应结束和本批结果，保留执行前权限及落库屏障。

对 agent-service：工具耗时可与剩余输出重叠，同时保留可审计的执行起点。这是同工作树并行完成的时序优化，不是服务化前置条件，也不承诺每种 Provider 都有延迟收益。
不是流式中断恢复
  • 缺少原始参数或完整结束事件时，回退到响应结束后的执行；不使用片段或修补 JSON 盲目启动。
  • 保留工具顺序、串行规则、结果复用及错误/取消收束，不重复执行提前完成的调用。
  • 最终 Assistant 提交后清除调用快照。若工具已启动但最终模型响应未提交就崩溃，保留快照和账本，拒绝盲目续跑，不伪造历史。

已有基线继续沿用，不重复算成本轮新功能

10 月 15–16 日已完成包级分层、宿主注入、按需正文、每轮卸载及增量事件。本轮扩展到元信息按需、整个 Session 回收和恢复闭环。token 增量与分页引导继续回归，但 Cloud 的完整快照消费者仍须迁移。事件 revision 与历史 seq 不是同一个游标，缺口须重建引导视图。

03 WHERE TAKEOVER STARTS

接手的是已保存的事实，不是旧进程的现场

Turn 是恢复任务；已提交消息是继续执行的安全边界。外部任务的关联让“工具结果暂缺”可以被查询，但不让未知结果自动变成成功。执行 checkpoint 与上下文压缩 checkpoint 用途不同，不能互相替代。

场景 A · 工具结果已经提交

不再执行工具
  1. 1. 输入已保存用户消息 + Turn checkpoint
  2. 2. 工具结果已保存结果与终态账本同事务
  3. 3. 实例 A 退出未提交的流式片段可能丢失
  4. 4. B 取得归属核对 checkpoint 与工具事实
  5. 5. 原 Turn 继续保存准入后，再请求模型

场景 B · 外部任务还在执行

不重新提交任务
  1. 1. 先保存关联原工具身份 + submission_intent
  2. 2. 执行器提交实际收到确认才记录 submitted
  3. 3. A 退出 / 丢响应远端任务可能继续运行
  4. 4. B 查询原 ID不依赖原 callback 或通知
  5. 5. 保存明确结果结果 + 终态账本 + 准入同事务
外部任务恢复行为：正常执行会查询等待；恢复入口不会替 Cloud 自动调度。
查询或故障情况PIE 的实际处理
running恢复返回 409，不推进；宿主之后可再次触发。
completed + 有效结果保存原工具结果，与终态账本及准入原子提交，再运行模型。
已知 failed / cancelled按工具错误结果进入原 Loop，不重新启动任务。
缺失 / unknown / 身份不符拒绝继续，不自动重提；完成状态缺少结果也拒绝。
丢提交响应 / 查询故障保留原关联与历史，不保存由本地中止产生的假工具错误。
只有提交意图，没有确认不能推断远端未执行；只查原任务，missing/unknown 继续阻断，不自动重提。
终态账本没有配套历史结果在查询执行器或创建 Agent 前拒绝，不能把不一致状态当作可恢复事实。
提前工具已启动，最终模型响应未提交保留 pendingAssistant 与 started 审计，不伪造历史，不盲目续跑。
服务关闭 vs 用户取消关闭只解除本地等待；显式取消先保存意图，再请求远端。不能据此断言副作用已撤销。
安全边界，不是功能缺陷

只有工具调用、没有结果且没有有效外部任务关联时，不能判断动作是否已经生效。宁可记录“未知”并阻断，也不能因重启把发送、支付或文件修改盲目再做一遍。

PIE 不承诺副作用恰好一次。实例内串行准入不是分布式锁；远端任务幂等、Worker 内部恢复与旧 owner 隔离，仍由宿主和执行器保证。

04 ONE LOOP, DIFFERENT HOSTS

复用执行语义，不强求相同宿主生命周期

agent-service 对应云端的产品宿主，承担与本地 astronverse-agent 相近的装配职责；不是把本地 Server 搬到云上。不同存储和工具通过契约接入同一份 Loop。

Local host

本地装配

packages/local 提供 SQLite、本机工具、Skill/MCP 与配置；packages/server 提供本地 HTTP/SSE、CLI/Sidecar。

Cloud host

agent-service

限定授权范围，注入共享存储、模型与工具能力，管理归属/路由/WS/SSE；不导入 Local/Server 实现。

共同复用 · packages/pie 下的五个共享包

runtime 会话/Turn/恢复语义 · agent 底层 Loop · ai 模型调用 · mcp 协议能力 · telemetry 观测契约

职责PIE 提供agent-service / 云端负责
执行Session/Turn、Loop、历史、分支、压缩和恢复入口产品 API、授权、请求路由与执行范围
存储按需读取、独立账本与历史/元信息/账本原子提交契约MySQL/Redis/对象存储、索引、事务、连接池

归属不把租约、Pod 或 Redis 协议写进 Loop认领、续约、代次校验、失租隔离和接管

本地使用不增加云端依赖

默认仍是 SQLite + retain。恢复通过 PI_TURN_RECOVERY=manual 显式开启；HTTP 增加恢复/取消入口；自带测试 UI 已移除，当前通过 SDK / HTTP / 嵌入契约验收，中断 Turn 处理前禁止新一轮输入。原工具、Skill/MCP、Subagent 和后台行为保持回归。

Runtime 列表默认分页 50 条，但本地封装按页汇总，HTTP GET /sessions 保持原完整列表形状。异步订阅已适配；旧数据库事务性迁移并建立索引，不要求删库重建。

本次 SQLite 新增独立账本表及索引，工具执行边界增加可靠写入，但不要求本地每轮销毁 Agent。完整工具调用可能更早启动；下一次模型请求仍等待结果，本地默认保留和恢复策略不变。

05 CLOUD ADOPTION

PIE 完成，不等于 agent-service 已经消费

沿用此前 2026-10-26 的 Cloud 本地源码只读核对：已有 MySQL 存储、执行归属/路由和工具执行层，不是从零搭建。本次文档更新未重新核对 Cloud 工作树，未运行 Cloud 测试或确认生产部署；以下是待增量接入项。

当前源码观察需要解决的接入差距
共享 Runtime / MySQL StoreCloud 副本仍使用 loadSessions()；需要实现按 ID、游标分页和 Turn 后缀读取。
RuntimeFactory已启用 release-after-turn，但仍全范围恢复和收集配置引用。仅升级 PIE 不能消除工厂预扫描。
RuntimeManager / 事件路由仍读取 event.snapshot 并构造 Cloud 快照事件；须同步增量契约、引导视图与历史补读。

建议服务端按这个顺序接入

  1. 五包三方增量合并

    固定基线，仅合并 runtime/agent/ai/mcp/telemetry，保留同事改动。不覆盖目录，不搬入 Local/Server 等本地宿主。

  2. 迁移 Store、账本与工厂

    实现 readSession、分页 listSessions、readTurnPath 与 readToolExecutions。saveSession 必须同事务保存历史、元信息和增量账本，不能忽略第三个参数或提交后补写；工厂按目标会话恢复与解析配置。

  3. 迁移增量事件链路

    await 会话订阅；处理分页初始视图、历史补读与序号缺口。Redis 路由、WS/SSE 和客户端都不能假定每个事件有完整 snapshot。

  4. 把租约与原 Turn 恢复衔接

    授权、认领与旧 owner 隔离在先；恢复使用原配置/prompt/Turn ID，不能把 resume 当作重新 submit。

  5. 用现有账本 / Worker 实现执行器

    注入 DurableJobExecutor，持久映射稳定 ID，保存状态与结果。通知可丢，但 get 必须能找到已提交事实。

  6. 联合故障与成本验收

    验证 A 退出/B 接手、丢通知/丢响应、DB 故障、取消、滚动更新、失租旧写入与长历史/大消息。健康 200 不能替代接管验收。

必须迁移的共享接口
  • loadSessions 删除：改为 readSession 与游标 listSessions。
  • readTurnPath 新增：校验分支，保留原节点身份并返回当前 Turn 后缀。
  • saveSession(session, replaceHistory?, toolExecutions?)：账本与历史/元信息同事务，按稳定记录 ID 去重，身份冲突拒绝。
  • readToolExecutions：按 Session、Turn 和独立 seq 在存储层分页，每页 1–200 条；清理 checkpoint 不删账本。
  • TurnCheckpoint.pendingAssistant：保留执行前调用快照，不能因最终消息未落盘就把工具判为未执行。
  • Runtime 列表消费 nextCursor；不能误把第一页当完整结果。
  • subscribe 返回 Promise，subscribeAll 仍同步；处理建立前连接关闭。
  • 消费 interrupted 与 resumeTurn；原 Turn 未处理完不提交下一轮。
  • jobs/runJob 为显式可选能力，原内存任务不会自动升级。

不能把这些写成“已完成”

Cloud 生产执行器、租约与恢复联合验收、持久确认和未保存队列、原内存后台/父子任务迁移、任意函数现场续跑，都不属于当前交付。没有承诺 RSS、吞吐或全链路字节上限，也未构建 Sidecar、部署或验收 Electron/Astron 实机链路。

执行账本不是完整事件溯源或任意步骤重放引擎，durable 标签也不替代执行器和租约。流式工具提前执行不提供流中断恢复，缺少完整调用事件时保守回退。
